# CPU correctness matrix (RQ1): design

Owner: Victoria · Plan: work distribution §6 "CPU correctness matrix" · Proposal: Evaluation Plan, workload, faults and baselines

This page fixes the design before the results. The numbers are generated by the script below into `report.md` and `runs.csv` next to the retained run directories. Copy results into the final report only from those files.

```cmd
.venv\Scripts\python.exe scripts\run_correctness_matrix.py --output-dir run-data\correctness-matrix
```

The default sweep is 558 runs (5/10/20 steps × seeds 33, 34, 35 × 62 cells); runtime depends on host and process-control overhead. `--resume` continues an interrupted sweep in the same directory. The exit code is 0 only if every OutcomeServe exit criterion holds, every declared case is present once, and all injections (including baselines) are valid. Baselines may correctly be reported as incorrect after a valid injection.

Before the first run the sweep writes `matrix-plan.json` (cases, settings, Python and platform, source hashes), `source-snapshot.zip` (the exact sources used, committed or not) and `git-head.txt`. `--resume` only continues when the plan, sources and environment are identical, checks each retained result against its case, and refuses half-written runs. A changed experiment goes into a new output directory; raw runs are never edited or replaced.

## Workload

`make_inventory_workload(..., tools="mixed")` cycles three C2 tools, as the proposal's order tasks require:

| Tool | Kind | Deduplication | Outcome query |
| --- | --- | --- | --- |
| `read_inventory` | Read | Yes | Yes |
| `decrement_inventory` | Non-idempotent write | Yes | Yes |
| `set_reorder_level` | Idempotent write | Yes | Yes |
| `notify_supplier` | Non-idempotent external call, outside C2 | No | No |

`notify_supplier` stands for an arbitrary API without the tool contract (proposal: "ambiguous outcomes are surfaced"). It is served by a separate endpoint of the tool process, records every submission as a new effect, and has no query and no epoch fencing. `with_external_step` replaces the faulted decrement with it, so the same task position forms a should-resume case (C2 decrement) and a should-abstain case (external call).

The default workload (`tools="inventory"`) is unchanged, so existing results, fixtures and the performance path are unaffected. Performance runs refuse to reset a database that contains external effects.

## Cells

Each fault is placed at the first step of the selected tool kind at or after the requested progress (0.5 by default). `actual_progress` records where it landed.

| Fault domain | Boundaries | Methods | Fault step tool |
| --- | --- | --- | --- |
| Runner crash | DURING_GENERATION, PRE_DISPATCH, POST_TOOL_COMMIT_PRE_RESULT_LOG, POST_CONTEXT_COMMIT | all four | decrement, idempotent, external |
| Dropped tool acknowledgment | POST_TOOL_COMMIT_PRE_RESULT_LOG | all four | decrement, idempotent, external |
| Crash during recovery (two faults) | DURING_RECOVERY | OutcomeServe | decrement, idempotent |

An external call has no reconciliation query, so it has no DURING_RECOVERY cell.

## Expected behavior

The experiment controls whether a tool supports outcome queries and whether the tool service is reachable, so the required behavior is fixed per cell in advance, not inferred from the final state:

- **abstain** when the faulted step is the external call and its outcome is unknown: a runner crash at PRE_DISPATCH or POST_TOOL_COMMIT_PRE_RESULT_LOG, or a dropped acknowledgment;
- **complete** everywhere else, including the external call at DURING_GENERATION (never sent) and POST_CONTEXT_COMMIT (outcome logged).

At PRE_DISPATCH the external call was in fact never sent, but no runner can establish that. Abstaining is required, and a baseline that continues counts as a missed abstention even though no duplicate results.

## Metrics

From the business verifier (final snapshot, all methods): duplicate effects (C2 decrements and external calls), tool-result and inventory mismatches, reorder-level mismatches, the effect audit, and `prefix_state_mismatches`, which compares state with the reference after exactly the steps that took effect, so that a correctly halted task can be judged. Executed steps must also form a contiguous workload prefix. External effect audits independently check tool identity, argument fingerprint, canonical result JSON, unique receipt and owner epoch. Missing or corrupt evidence is never treated as zero duplicates.

From the protocol verifier (OutcomeServe): the durable-log invariants, with checkpoint `halted` for abstained runs.

From the worker event trace (`outcomeserve/verify/decisions.py`), because a final snapshot cannot show retry decisions:

| Metric | Definition |
| --- | --- |
| Unsafe retry | Resubmitting a non-idempotent step after an earlier submission, without an authoritative NOT_COMMITTED in between |
| False abstain | Abstaining in a cell that requires completion |
| Missed abstain | Continuing in a cell that requires abstention |
| Continued after abstain | Submissions or completions after the halt (any step), or later steps found in the effect audit, whichever is larger |

A run is **correct** when it shows the required behavior, has no duplicate effect, no unsafe retry, no effect after an abstention, a complete audit, no tool-result mismatch and state consistent with the executed steps. For OutcomeServe the protocol verifier must also pass.

Decision metrics need a usable worker trace: nonempty, on one clock, ordered, with nondecreasing epochs, a `TOOL_SUBMIT` for every step that took effect, and exactly one matching halt event when the runner abstained. Otherwise the metrics are unknown (null), the run is not correct, and the tables show `unknown` instead of summing it as zero. `passed` still means verified task completion, so a required abstention is `correct: true, passed: false`. Restarting an abstained OutcomeServe task returns exit 3 without calling any tool or writing a record.

## Exit criteria (OutcomeServe)

These come from work distribution §6. The script evaluates them from `runs.csv`:

1. No invalid OutcomeServe runs.
2. Zero duplicate effects for supported C2 tools.
3. Zero unsafe retries, and abstention whenever an outcome is UNKNOWN.
4. No continuation after RECOVERY_ABSTAIN.
5. No false abstention when the outcome is establishable.
6. A repeated crash during recovery preserves the invariants.
7. Model errors are reported separately. Not applicable here: CPU runs use scripted traces without model inference.

## Scope

These are CPU runs with scripted traces. They establish protocol behavior at the fault boundaries, not GPU timing or model behavior. Seeds vary the inventory quantities and SKUs. The matrix observes zero violations in these cells; it is not a proof for arbitrary interleavings.
